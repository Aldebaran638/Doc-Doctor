## 一、Git 函数内容变更警告（problem_type = 4）

### 1.1 功能概述

在“项目检查”时，Doc-Doctor 会尝试使用 VS Code 自带的 Git 扩展，对当前分支最新两次提交 `HEAD~1` 与 `HEAD` 的差异做分析：

- 仅针对 **发生过实质内容变更的 .c 文件** 做检测。
- 对比同一函数在 `HEAD~1` 与 `HEAD` 中的函数体：
  - 忽略空白字符（空格、缩进、换行等）。
  - 忽略所有行注释 `// ...` 和块注释 `/* ... */` 的变更。
- 若忽略上述差异后，函数体仍不完全相同，则认为“该函数内容发生了变更”，生成一条 **problem_type = 4** 的问题：
  - `problemDescription` 固定为：
    > 函数体相对于上一次提交发生变更，请检查注释是否同步更新。
  - `functionSnippet` 为当前函数体前 200 个字符。

### 1.2 开关与前置条件

- 配置项：
  - `doc-doctor.enableGitChangeWarning`: `boolean`，默认 `true`。
  - 目前由服务层直接从 VS Code 配置中读取，前端如需提供 UI 可以把它做成一个开关。
- 仅在调用 **项目检查** 时生效（消息 `runProjectCheck`）。
- 仓库需满足：
  - 使用 Git 管理；
  - 至少有两条提交历史（从第二次提交开始才有可比较的 `HEAD~1`）。

### 1.3 相关服务层代码位置

- 入口：
  - [src/modules/projectCheck.ts](src/modules/projectCheck.ts)
  - 导出函数：`checkAllFiles`、`runProjectCheck`。

- Git 变更分析核心逻辑（简述）：
  - 在 `checkAllFiles` 内部：
    1. 通过 `vscode.extensions.getExtension("vscode.git")` 获取 Git 扩展 API；
    2. 找到当前工作区对应的 `Repository`；
    3. 调用 `repo.log({ maxEntries: 2 })` 检查提交数量；
    4. 调用 `repo.diffBetween("HEAD~1", "HEAD")` 获取变更文件列表；
    5. 过滤出所有以 `.c` 结尾的文件，记入 `changedCFiles`；
    6. 对每个变更的 `.c` 文件，用 `repo.show("HEAD~1", fsPath)` 取出旧版源码，并调用 `parseFileContent` 解析函数列表，将 `(filePath, functionSignature) -> FunctionInfo` 存入 `oldFunctionsByFile`；
    7. 在遍历当前版本函数时，如果函数所在文件在 `changedCFiles` 中，且在 `oldFunctionsByFile` 中能找到同签名函数，就调用 `hasFunctionBodyChangedIgnoringWhitespaceAndComments(oldBody, newBody)` 判断是否有实质变更；
    8. 如果有实质变更，则追加一条 `ProblemType.CONTENT_CHANGED`（枚举值为 `4`）的问题到返回结果。

- 比较函数：
  - `hasFunctionBodyChangedIgnoringWhitespaceAndComments(oldBody: string, newBody: string): boolean`
  - 作用：
    - 去掉块注释：`/\*[\s\S]*?\*/`。
    - 去掉行注释：`//.*`（逐行处理）。
    - 去掉所有空白字符：`\s+`。
    - 比较剩余字符串是否完全一致。

### 1.4 与前端的数据交互

#### 1.4.1 问题对象结构扩展

本次功能沿用既有 `ProblemInfo` 结构，没有新增字段，仅在原有问题类型上增加 `problem_type = 4` 的语义：

- `problemType: 4`：内容变更警告（`ProblemType.CONTENT_CHANGED`）。
- 其他字段保持不变：
  - `filePath: string`
  - `functionName: string`
  - `functionSignature: string`
  - `lineNumber: number`
  - `columnNumber: number`
  - `problemDescription: string`
  - `functionSnippet: string`

前端在渲染问题列表时，如需特别高亮“变更警告”，只需在原有 `typeLabel` 映射中对 `4` 做对应展示即可（当前实现中已存在 `case 4: '变更警告'`）。

#### 1.4.2 Git 状态提示消息

为方便用户了解是否启用了 Git 检测，服务层在执行项目检查后会通过 `webview.postMessage` 额外发送一条 **日志类消息**：

- 消息类型：`log`
- 数据结构：
  ```ts
  webview.postMessage({
    type: "log",
    message: result.gitMessage, // string
  });
  ```

`gitMessage` 的可能取值示例：

- `Doc-Doctor: 未找到 Git 扩展，已跳过内容变更检测。`
- `Doc-Doctor: 当前项目未使用 git，已跳过内容变更检测。`
- `Doc-Doctor: 当前仓库历史不足两条提交，已跳过内容变更检测（仅从第二次提交开始启用）。`
- `Doc-Doctor: 无法解析历史版本函数信息，已跳过内容变更检测。`
- 或 Git 相关异常时的错误信息。

前端可以选择：

- 在现有的 `log` 分支下，将 `message` 追加到输出区域（当前 sidebar.js 已有该逻辑）。
- 或在 UI 某处专门展示 Git 检测状态。

## 二、AI 辅助 Doxygen 注释生成 / 更新

> 当前仓库中已去掉前端“AI 按钮”等 UI 逻辑，但服务层接口和配置仍然生效，方便未来重新接入。

### 2.1 功能概述

服务层提供一个通用的“AI 生成 / 修复注释”能力：

- 输入：一条已存在的“问题记录”（`ProblemInfo`），通常是：
  - 参数说明缺失（problem_type = 1），
  - 返回值说明缺失（problem_type = 2），
  - 函数功能说明缺失（problem_type = 3），
  - 或内容变更警告（problem_type = 4）。
- 服务层会：
  1. 根据问题信息重新解析对应的函数源码与注释；
  2. 拼接一个 JSON payload 调用外部 AI HTTP 接口；
  3. 从 AI 返回结果中取出一段 Doxygen 注释；
  4. 进行一次轻量级的 Doxygen 结构补全校正（确保有 `@brief`, `@param`, `@return` 等标签）；
  5. 将校正后的注释文本返回给前端，由前端决定如何展示与写回源文件。

### 2.2 配置项

服务层从 VS Code 全局设置 `doc-doctor` 节下读取以下配置：

- `doc-doctor.enableAIRefactor`: `boolean`
  - 是否启用 AI 辅助更新注释功能。默认 `false`。
  - 若为 `false`，调用 AI 相关接口会抛出异常，提示“功能未启用”。

- `doc-doctor.ai.endpoint`: `string`
  - AI 服务 HTTP 接口地址，例如：`http://localhost:3000/doc-doctor/ai-comment`。
  - 必须返回 JSON，至少包含 `newComment: string` 字段。

- `doc-doctor.ai.apiKey`: `string`
  - 调用 AI 服务使用的 API Key。
  - 服务层会在请求头中加入：`Authorization: Bearer <apiKey>`。

> 前端如果需要提供设置 UI，可以读写以上三个配置键。

### 2.3 相关服务层代码位置

- AI 业务模块：
  - [src/modules/aiRefactor.ts](src/modules/aiRefactor.ts)
  - 导出函数：`generateCommentWithAI(problem: ProblemInfo): Promise<{ newComment: string }>`。

- Webview 消息接入（服务层）：
  - [src/extension.ts](src/extension.ts)
  - 在 `onDidReceiveMessage` 中新增处理分支：
    - `type: "aiFixComment"`：接收前端传来的 `problem`，调用 `generateCommentWithAI`，再通过 `aiFixPreview` / `aiFixError` 将结果回传前端。

> 当前仓库的前端 sidebar.js 中已移除与 `aiFixComment` / `aiFixPreview` / `aiFixError` 相关的逻辑，因此服务层这两种消息类型暂时不会被触发；后续如需恢复前端按钮，可直接按本节描述的协议对接。

### 2.4 generateCommentWithAI 调用流程

`generateCommentWithAI(problem)` 的主要步骤：

1. 读取 VS Code 配置：
   - `enableAIRefactor`、`ai.endpoint`、`ai.apiKey`。
   - 若未启用或配置不完整，直接抛出带有明确提示信息的异常。

2. 通过 `getFunctionContextFromProblem(problem)` 重新解析函数：
   - 使用 `problem.filePath` 打开文档并读取全文；
   - 复用 `parseFileContent` 解析函数列表；
   - 优先按 `(functionSignature, lineNumber)` 精确匹配；若失败，退化为仅按 `functionSignature` 匹配；
   - 失败时抛出“在文件中未找到与问题对应的函数”错误。

3. 构造 AI 请求 payload：
   ```ts
   const payload = {
     filePath: problem.filePath,
     functionName: problem.functionName,
     functionSignature: problem.functionSignature,
     problemType: problem.problemType,
     existingComment: funcInfo.comment,        // 可能为空
     functionBody: funcInfo.functionContent,   // 函数完整源码
     language: "zh" | "en",                    // 基于现有注释是否包含中文判断
     gitDiff: string | undefined,              // 若为变更警告，附带 HEAD~1 vs HEAD 的 diff 片段
   };
   ```

4. 通过 `fetch` 调用外部 AI HTTP 接口：
   ```ts
   const res = await fetch(endpoint, {
     method: "POST",
     headers: {
       "Content-Type": "application/json",
       Authorization: `Bearer ${apiKey}`,
     },
     body: JSON.stringify(payload),
   });
   ```

5. 解析返回：
   - 期望响应体为 JSON，结构中至少包含：
     - `newComment: string`（或兼容旧字段名 `comment: string`）。
   - 若 HTTP 状态非 2xx 或 JSON 结构缺失 `newComment`，会抛出带有详细状态码和响应文本的异常。

6. Doxygen 注释结构修正：
   - 使用 `fixDoxygenComment(rawComment, funcInfo)` 对 AI 生成的文本做一次轻校正，保证：
     - 是一个 `/** ... */` 形式的块注释；
     - 若原注释缺少 `@brief`，自动补上一行带“由 AI 自动生成，建议人工审阅”的说明；
     - 针对 `functionSignature` 中解析出的每个参数名，确保都有对应的 `@param` 行；
     - 若函数返回类型不是 `void`，确保存在 `@return` 行；
     - 中文 / 英文提示文案会根据 `language` 选择。

7. 返回结果：
   - `generateCommentWithAI` 只返回：
     ```ts
     { newComment: string }
     ```
   - 如何在前端展示或写回源码，完全由前端决定。

### 2.5 与前端的消息协议（建议）

以下协议是服务层目前已经实现、但前端暂未对接或已移除的部分，前端可按需恢复：

1. 前端请求 AI 修复：

   - 发送消息：
     ```js
     vscode.postMessage({
       type: 'aiFixComment',
       data: { problem },  // problem 为一条 ProblemInfo
     });
     ```

2. 服务层处理逻辑（extension.ts 中）：

   - 伪代码：
     ```ts
     case "aiFixComment": {
       const problem = message?.data?.problem as ProblemInfo;
       try {
         const { newComment } = await generateCommentWithAI(problem);
         webview.postMessage({
           type: "aiFixPreview",
           data: { problem, newComment },
         });
       } catch (e) {
         const msg = (e as Error).message || String(e);
         vscode.window.showErrorMessage("AI 修复注释失败：" + msg);
         webview.postMessage({
           type: "aiFixError",
           message: msg,
         });
       }
       break;
     }
     ```

3. 服务层返回结果消息类型：

   - `aiFixPreview`：
     ```ts
     {
       type: "aiFixPreview",
       data: {
         problem: ProblemInfo,
         newComment: string,
       },
     }
     ```

   - `aiFixError`：
     ```ts
     {
       type: "aiFixError",
       message: string, // 错误信息
     }
     ```

前端在需要的时候，可以为某些问题类型（1/2/3/4）重新增加按钮或菜单项，调用上述协议，实现从“点击 AI 修复”→“展示预览”→“用户确认后写回源码”的完整交互。

    - `generateCommentWithAI(problem)`：对外核心入口；

## 三、开发流程总结

### 前端开发者：

## 四、常见问题

### Q1: 如何调试前端代码？
**A:** 按 F5 启动扩展调试，打开侧边栏后按 `Ctrl+Shift+P` 输入 "Developer: Open Webview Developer Tools" 查看控制台。

### Q2: 前端修改后不生效？
**A:** 重新加载窗口（`Ctrl+R`）或重启扩展（F5 重新调试）。

### Q3: C++ 如何返回错误信息？
**A:** 在 JSON 中添加 `error` 字段：
```json
{ "success": false, "message": "数据库连接失败", "error": "..." }
```

### Q4: 数据库文件存放在哪里？
**A:** `<当前工作区根目录>/doc-doctor/database/problems.db`

### Q5: 如何处理大量数据？
**A:** 可以添加分页接口：
```cpp
extern "C" const char* loadProblemsWithPagination(int page, int pageSize);
```
